# 一页讲清方法：研究、设计、计划

这一页讲的是 pstack 在写代码之前怎么决定「该做什么」。内容压缩自上游作者的 [The Complete Guide to pstack Pt. 2](https://x.com/poteto/status/2097732320606507506)，并落到本仓库在 Codex 上的实际做法。

想要手把手的版本，看 [指南](guide/README.md)。想先知道 playbook 为什么这么排，看这一页。

## 要解决的两个问题

模型越来越强，但下面两种失败还是反复出现：

1. agent 没搞懂你要什么，因为需求本身写得太薄。
2. agent 没有做对这件事所需要的上下文。

两个都是上下文问题。下面这套流程，一是把更好的上下文交到 agent 手里，二是让你不用逐行读代码也能判断它做得对不对。

## 先说目标，再让它复述

现在的模型写代码比大多数人逐行监督的水平要高。所以要说清楚目标，而不是敲键步骤。然后，在任何代码出现之前，先要一遍复述：

```text
$poteto-mode read this thread. restate the underlying issue in your own words, in plain english. don't change any code yet.
```

这一步有三个作用。把嘈杂的讨论压成一句问题陈述；在改动只有一个消息的距离时暴露误读；以及，不把自己的猜测写进提示词，免得把 agent 带偏。

## 用四个技能建立心智模型

| 技能 | 回答什么问题 |
| --- | --- |
| `$how` | 代码现在在运行时到底怎么走 |
| `$why` | 它为什么长成这样，从历史和工单里找 |
| `$pstack-teach` | 把两者揉成一段你能核对的解释 |
| `$recall` | 你自己在这个话题上做到哪了 |

`$why` 不只看版本历史，还会查你接入的 MCP 能提供的证据：PR 评论、工单、设计文档、群聊、错误监控、分析数据。查不到就如实说查不到，因为「没人写下原因」本身也是答案。

`$recall` 对跨天的工作很关键。新开的 agent 上下文是空的，recall 从你的会话记录和共享记录里把上下文补回来，不用每天早上重新铺一遍。

这件事会复利。一个必须解释自己推理过程的 agent，会去读代码、给每个结论找依据，而不是自信地说一句就往下走。

## 用代码做设计，不要用文字做设计

用 agent 做规划，最常见的两个错误：接受模型给出的第一个设计；写一份很长、但没有任何代码验证过的计划。

两种都靠同一个办法解决：让 agent 用「跑一下」来回答自己的开放问题，而不是等你拍板。

如果产物是给别的代码调用的包或 API，先写教程。把 API 描述给一个假想的用户，实现就从调用点反推出来。`$technical-writing` 保证这份文档只做一种文档模式，不会一边当教程一边滑向参考手册。这份文档同时成了 agent 自检的目标。

如果是设计决策，用 `$architect`。它先摸清这块改动涉及的现有系统，再用 `$arena` 并行产出几份互相竞争的设计草图，由另一个模型家族的评审打分，最后按胜出的方案实现。如果实现时发现同一套绕行写法出现在不相关的地方，或者类型要靠 `any` 才能编译，那就说明设计错了，整个扔掉重来，而不是打补丁。

如果是开放问题，用原型 playbook：

```text
$poteto-mode prototype a few options for the new dropdown menu. take screenshots or videos for me to compare.
```

原型是一次性的。你从跑起来的东西里挑，而不是从描述里挑。这个 playbook 同样适用于行为和时序，不只是界面布局。

## 计划放到最后写

pstack 故意没有规划技能。在设计还没站住的时候写的计划，只是一个排过版的猜测。

等设计稳定下来，多阶段计划 playbook 把它拆成一串小的 PR。每个任务都围绕证据来组织。光有测试不算验证；一步只有在真正跑过、证据存在时才算验证。

```text
$poteto-mode turn this design into a plan. small verifiable PRs, each with its own verification steps.
```

执行之前，有脚本先检查计划的结构。计划本身就是交付物，什么时候开始执行由你说了算。

## 本移植版的差异

方法是作者的，本仓库只改编排，不改思路：

- `/teach` 在这里叫 `$pstack-teach`，因为 `teach` 是常见技能名，而 Codex 不会合并同名技能。
- Codex 没有 Custom Modes，所以 `$poteto-mode` 要按任务显式调用；除 `setup-pstack` 外，所有技能都只接受显式调用。
- `$how`、`$why`、`$recall` 读的是 `$CODEX_HOME/sessions` 下的 Codex 会话日志，不是 Cursor 的记录。
- 用 `$create-verification-skill` 生成的验证技能，会按仓库实际情况选驱动方式：已有的测试框架、浏览器与 CDP、PTY，或者纯 HTTP。

## 这里不声称的事

上游作者说她用这套方法在 2026 年 8 月向生产环境提交了 2,462 个 PR。那是她在自己代码库上的结果，不是这个移植版的基准。本仓库没有遥测，目前也没有自己的效果数据。[怎么判断效果](../README.zh-CN.md#怎么判断效果) 讲了怎么在自己的仓库里测。
